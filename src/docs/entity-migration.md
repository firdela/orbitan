# OrbitanOS — Entity Migration Guide
> **Product Owner:** Muhammad Firdaus Bin Ismail, Founder — Orbitan  
> **Version:** 1.0.0  
> **Date:** 2026-06-04  
> **Purpose:** A step-by-step guide for exporting OrbitanOS entity schemas and data records to any target database.

---

## Overview

All OrbitanOS data is stored as structured JSON documents, scoped by `tenant_id`. Every entity schema is defined in `/entities/*.json` as a JSON Schema object. This makes migration straightforward — the schemas map directly to database tables or collections in any modern database.

## Step 3 — Target Database Mapping

### Option A: PostgreSQL (Recommended for Enterprise)
Map each entity to a relational table. Use JSONB columns for array/object fields.

```sql
-- Example: InventoryItem
CREATE TABLE inventory_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id UUID NOT NULL REFERENCES tenants(id),
  outlet_id UUID REFERENCES outlets(id),
  name VARCHAR(255) NOT NULL,
  sku VARCHAR(100),
  category VARCHAR(100),
  unit VARCHAR(50) NOT NULL,
  current_stock DECIMAL(10,3) DEFAULT 0,
  par_level DECIMAL(10,3),
  reorder_point DECIMAL(10,3),
  cost_per_unit DECIMAL(10,2),
  supplier_id UUID REFERENCES suppliers(id),
  is_ingredient BOOLEAN DEFAULT FALSE,
  storage_location VARCHAR(255),
  expiry_tracking BOOLEAN DEFAULT FALSE,
  status VARCHAR(50) DEFAULT 'active',
  notes TEXT,
  created_date TIMESTAMPTZ DEFAULT NOW(),
  updated_date TIMESTAMPTZ DEFAULT NOW(),
  created_by_id UUID
);
```

### Option B: MongoDB / DocumentDB
Each entity maps directly to a MongoDB collection. No transformation needed — the JSON export from Base44 can be inserted directly using `mongoimport`.

```bash
mongoimport \
  --db orbitanos \
  --collection inventory_items \
  --file inventory_items_export.json \
  --jsonArray
```

### Option C: Supabase (PostgreSQL + Auth)
Supabase is the closest 1:1 replacement for Base44's backend. It provides:
- PostgreSQL database (use the schema from Option A)
- Row-Level Security (RLS) — replicate the RLS rules from each `/entities/*.json` file
- Auth — replace `base44.auth` with `supabase.auth`
- Edge Functions — replace `/functions` with Supabase Edge Functions (Deno-compatible, minimal changes)

## Step 4 — Replicate Row-Level Security (RLS)

Every entity in OrbitanOS enforces tenant isolation via RLS rules. When migrating, these rules must be replicated in your target database.

### Example: InventoryItem RLS in PostgreSQL
```sql
-- Enable RLS
ALTER TABLE inventory_items ENABLE ROW LEVEL SECURITY;

-- Tenant isolation policy
CREATE POLICY tenant_isolation ON inventory_items
  USING (tenant_id = current_setting('app.current_tenant_id')::UUID);

-- Role-based access: outlet_manager and supervisor can read
CREATE POLICY outlet_read ON inventory_items
  FOR SELECT
  USING (
    outlet_id = current_setting('app.current_outlet_id')::UUID
    AND current_setting('app.current_role') IN ('outlet_manager', 'supervisor', 'worker')
  );
```

The source of truth for each entity's RLS rules is the `"rls"` block in `/entities/*.json`.

## Step 5 — Migrate Auth

### Current Auth (Base44)
```javascript
const user = await base44.auth.me();
// Returns: { id, email, full_name, role, data: { tenant_id, outlet_id } }
```

### Target Auth (Standard JWT)
Replace with any JWT provider. The user object shape must remain the same for all functions and pages to work without changes:
```javascript
// Expected shape after migration:
{
  id: "uuid",
  email: "user@example.com",
  full_name: "Jane Doe",
  role: "outlet_manager",
  data: {
    tenant_id: "uuid",
    outlet_id: "uuid"
  }
}
```

## Step 6 — Validate Migration

After migrating, run these validation checks:

### Data Integrity
- [ ] All records have matching `tenant_id` values
- [ ] Foreign key relationships intact (e.g., `PurchaseOrder.supplier_id` → `Supplier.id`)
- [ ] Array/object fields correctly preserved (e.g., `PurchaseOrder.items`, `Recipe.ingredients`)
- [ ] `created_date` and `updated_date` timestamps preserved

### Functional Checks
- [ ] Clock-in/out records correctly linked to Employee and Shift records
- [ ] FinanceMapping records correctly link Orbitan records to Xero GUIDs
- [ ] ReplenishmentAlert records linked to InventoryItem records
- [ ] ProductCatalog records linked to MaterialCollection records (Retail Pack)

### Security Checks
- [ ] Tenant A cannot read Tenant B's records
- [ ] Worker role cannot access financial records
- [ ] Admin role has full access across all tenants
