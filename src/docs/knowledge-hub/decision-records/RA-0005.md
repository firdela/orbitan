# RA-0005: Orbitan Identity Architecture

> **Status:** FROZEN — 2026-07-23
> **Version:** 1.0.0
> **Type:** Reference Architecture
> **Supersedes:** None
> **Superseded by:** None
> **Related:** RA-0000, RA-0004, ADR-0048 (Orbit Identity Model)

## Decision

RA-0005 defines the Orbitan Identity Architecture — the final foundational pillar before
Build Mode. It binds the Orbit Identity Model (OIM) to tenant-isolated operational
reality, making Identity a governed Access Engine for the entire ecosystem, not merely
a user-login concern.

## Orbit Identity Model (OIM) Principles

1. **Global vs Local:** The `User` entity is the global persistent identity; the
   `Employee` entity is the tenant-scoped operational membership.
2. **Multi-Role / Multi-Tenant:** One `User` ID resolves to multiple `Employee` records
   (one per tenant/organisation) through a governed `MembershipResolver`.
3. **Zero-PII Isolation:** PII (email, phone) lives in the `User` record. Operational
   records (ClockRecord, AuditLog) reference the Employee/User id but MUST NOT store
   raw PII.
4. **Non-Human Identity:** AI Agents and Service Accounts are first-class identities with
   assigned `IdentityRole` records and strict capability-gated authorization. Future
   identity types (IoT devices, external integrations) are accommodated as governed
   principals under the same framework — not special cases.

## Organizational Topology

```
Platform Tenant (Platform Admin)
      ↓
Tenant (Enterprise Org)
      ↓
Company / Brand (Logical grouping)
      ↓
Outlet (Physical/Virtual operating unit — unit of operational isolation)
```

**Access Context:** Every request carries `{tenant_id, outlet_id, user_id, membership_id}`.
This becomes the basis for auditing, authorization, observability, and policy evaluation.

## Membership & RBAC/ABAC Engine

- **Resolution Pattern:** Every access check goes through `MembershipResolver` (PC-0002).
- **Governance Integration:** Access is computed at runtime by intersecting
  `Membership` + `ShieldPolicy` (Shield domain) + `ModuleAccessPolicy`.
- **Least Privilege:** Default state is "no access." Permissions are additive and
  governed by the `ActivationRegistry` pack.

## Service-to-Service Identity (Spiffe-lite)

- **Nexus-Authenticated Requests:** Platform services use short-lived nexus-gateway
  authenticated tokens carrying the user's effective identity.
- **Agent Identity:** Autonomous agents perform actions using an `agent_id` bound to a
  `ShieldPolicy` (governance threshold gate).

## Deferred Enhancements (Non-Blocking — Post-MVP)

These are worthwhile later but do NOT delay Build Mode:

- **Identity Lifecycle:** Invited → Active → Suspended → Disabled → Archived.
- **Authentication Policy:** Separate authentication (Password, Passkeys, SSO, MFA) from
  authorization.
- **Session Governance:** Session expiry, token refresh, device trust, logout propagation.
- **Delegation:** Acting on behalf of, temporary delegated authority, approvals.

## Trade-offs

- **Benefit:** Supports consultants, franchise operators, part-time workers, shared
  service staff, MSPs, and contractors across Orbitan without duplicating identities.
  Enterprise-grade context-aware authorization.
- **Cost:** MembershipResolver adds a resolution hop per access check — mitigated by
  runtime caching and the fact that access is computed once per request context.

## Amendment Rule

Changes to RA-0005 require a new ADR + Product Authority approval. The deferred
enhancements above are candidates for governed ADRs during/after MVP delivery, not
amendments to this frozen RA.
