# RA-0004: Orbitan Platform Services Architecture

> **Status:** FROZEN — 2026-07-23
> **Version:** 1.1.0
> **Type:** Reference Architecture
> **Supersedes:** None
> **Superseded by:** None
> **Related:** RA-0000, RA-0005

## Decision

RA-0004 defines how the Orbitan platform itself is constructed — separating Platform
Services from Domain Services and codifying the Platform Capability Principles that
protect Orbitan from becoming a monolith.

## Platform Capability Principles (PCP)

- **PCP-001:** Capabilities are reusable, tenant-agnostic services.
- **PCP-002:** Capabilities expose stable contracts, not internal implementations.
- **PCP-003:** Capabilities MUST NOT contain domain-specific business rules.
- **PCP-004:** Capabilities are independently versioned and governed.
- **PCP-005:** Capabilities MUST be observable, resilient, and traceable.

## Service Layering (Separation of Concerns)

```
Platform Layer  →  Domain Layer  →  Feature  →  UI
```

**Reverse dependencies are strictly prohibited.** This single rule protects Orbitan from
slowly becoming a monolith.

### Platform Services
Identity, Authorization, Nexus Gateway, Audit, Notification, Search, Storage,
Configuration, Policy, AI, Observability, Secrets, Feature Flags.

### Domain Services
Workforce, Finance, Procurement, Inventory, CRM, Scheduling, Attendance.

## Platform Service Invariants

Every Platform Service MUST comply with:
- **Statelessness** (where appropriate)
- **Tenant Awareness** (every operation carries `tenant_id` context)
- **Idempotency** (mutations support idempotency keys)
- **Observability** (structured logging + correlation ID propagation)
- **Least-privilege access**
- **Backward-compatible APIs**
- **Graceful Degradation** (fail closed/safe)

## Orbit Nexus — AI Platform Capability

Nexus is more than a gateway. It is the platform's AI capability layer, responsible for:
- AI routing, tool registry, agent registry, prompt registry
- Memory + vector search (RAG, domain + tenant scoped)
- AI governance (Sanitization Gate integration)
- Model selection + cost optimisation
- Policy enforcement for AI interactions

## Event & Resilience Architecture

- **Asynchronous Events:** Domain events, platform events, audit events, notification
  events, integration events — directional principles established even where
  implementation is deferred.
- **Resilience Standards:** Circuit breakers on external syncs; configurable timeouts
  (default 5s); exponential backoff retries for transient failures; idempotency.
- **Error Classification:** Validation, Authorization, Policy, Business Rule, Dependency,
  Infrastructure, AI, External Integration.

## Service Lifecycle

Each Platform Service defines: Draft → Active → Deprecated → Retired.
Aligned with RA-0000's governance lifecycle.

## Observability Standards

Structured logging, metrics, tracing, correlation IDs, health checks, service version
reporting — minimum standards enforced across all services.

## Trade-offs

- **Benefit:** Long-term maintainability; architectural erosion prevented by dependency
  rules; Nexus positioned correctly as the AI operating layer.
- **Cost:** Slightly higher ceremony for cross-layer changes; mitigated by governed ADRs.

## Amendment Rule

Changes to RA-0004 require a new ADR + Product Authority approval. Platform Capability
Registry additions (new capabilities) are governed by the RA-0000 ADL process, not by
amending this frozen RA.
