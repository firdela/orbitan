## Milestone 3.1 — Temporal Foundation

**Scope:** Introduce deterministic, injectable time and temporal
filtering of role assignments, plus structural validation of the
normalized Membership — all pure, all dependency-free.

### Components

| Component | Path | Responsibility |
|-----------|------|----------------|
| Clock | `src/lib/access/clock.js` | Injectable `now()` — `SystemClock` (prod) / `FixedClock` (tests). Decouples temporal logic from wall-clock. |
| MembershipValidator | `src/lib/access/membership/MembershipValidator.js` | Pure structural check of normalized Membership. Returns `{ valid, errors, invalid }`. Never throws. Distinct from null (`NO_MEMBERSHIP`). |
| RoleAssignmentResolver | `src/lib/access/membership/RoleAssignmentResolver.js` | Temporal filter: maps each assignment to `ACTIVE`/`PENDING`/`SUSPENDED`/`EXPIRED`/`REVOKED` at the clock's `now()`. Suspended/revoked memberships yield no active assignments. |

### Key design rules

- **Temporary runtime IDs:** `assignment_id` values generated by the
  resolver (`ra_<source>_<index>`) are ephemeral correlation keys for
  the current evaluation ONLY. They MUST NOT be persisted or used as
  foreign keys. Immutable assignment UUIDs arrive in a future ADR.
- **Resolver metadata:** every resolver exposes `name` + `version`
  (and `clockVersion` where relevant) so future audit logs record the
  exact pipeline state that produced a decision.
- **Pure composition:** no resolver imports the Base44 SDK. All data
  sources are injected.

### Tests

- `runTemporalTests.js` — Clock, Validator, RoleAssignmentResolver
  (temporal windows, statuses, factory metadata).

## Milestone 3.2 — Membership Provider Abstraction

**Scope:** Introduce a formal, versioned `MembershipProvider` contract
so the Access Engine depends on `provider.resolve(identity, context)`
instead of any specific identity source. RLS / Base44 / Employee
become an implementation detail of one provider, not an architectural
dependency of the pipeline.

### The architectural rule (documented per ADR-0050)

> The Membership Provider is the sole boundary responsible for
> converting external identity sources into the internal Membership
> contract. All downstream authorization components consume
> Membership only and remain independent of the underlying identity
> implementation.

### Contract (frozen at v1.0)

```
MembershipProvider v1.0
  resolve(identity, context) -> Membership | null
  - MUST return a normalized Membership on success
  - MUST return null when no membership exists
  - MUST throw on infrastructure error (pipeline fails closed)
  - MUST NOT return an invalid/partial shape
```

### Implementations

| Provider | Path | Source |
|----------|------|--------|
| EmployeeBase44Provider v1.0 | `src/lib/access/providers/EmployeeBase44Provider.js` | Base44 Employee entity via SDK. **The ONLY access-layer file that imports the Base44 SDK, queries Employee, or understands the legacy Employee schema.** Uses `translateEmployee` (the Compatibility Matrix adapter) and returns a normalized Membership. |
| MockMembershipProvider v1.0 | `src/lib/access/providers/MockMembershipProvider.js` | Pure, SDK-free, returns pre-seeded Memberships. Simulates how a future Entra / Google Workspace / LDAP provider behaves. |

### Migration boundary (preserved)

Only `EmployeeBase44Provider` knows the Employee schema. Everything
downstream — `MembershipValidator`, `RoleAssignmentResolver`,
`PermissionResolver`, `AccessPipeline` — consumes Membership only.
Swapping the identity source (Base44 → backend function → Entra → LDAP)
is a one-line provider change; nothing in the Access Engine changes.

### Pipeline (`src/lib/access/pipeline.js`)

`createAccessPipeline({ provider, clock })` composes:
`Provider → Validator → RoleAssignmentResolver → PermissionResolver → Decision`

Fail-closed mapping:

| Failure | Denial reason |
|--------|---------------|
| No identity | `unauthenticated` |
| Provider throws | `provider_error` |
| Provider returns null | `no_membership` |
| Invalid membership shape | `invalid_membership` |
| Membership not active | `membership_inactive` |
| No active assignments | `no_permission` |

Each stage emits `name` + `version` in `metadata` for audit.

### New denial reasons (additive to `DecisionObject`)

- `PROVIDER_ERROR: 'provider_error'`
- `INVALID_MEMBERSHIP: 'invalid_membership'`

These extend the ADR-0050 denial vocabulary without changing existing
semantics.

### Tests

- `runProviderIntegrationTests.js` — provider boundary (valid, missing,
  suspended, tenant mismatch, exception, multiple records, unknown
  status) + EmployeeBase44Provider migration boundary with mock SDK.
- `runPipelineTests.js` — end-to-end composition, fail-closed paths,
  audit metadata, construction guards.

## Strategic alignment

This separation of **identity retrieval**, **membership
normalization**, and **authorization evaluation** is the foundation
that makes OrbitanOS evolvable: the engine is stable while the identity
layer can change over time without ripple effects. It also keeps the
Access Engine Exit-Ready — the pure modules (clock, validator,
resolvers, pipeline, mock provider, contract) carry zero Base44
dependency and are portable to any stack.
